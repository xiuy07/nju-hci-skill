# 原则驱动的设计评审

## 定位用户的困难

执行/评估周期：形成目标、形成意图、明确动作、执行、感知状态、解释状态、评价结果。执行隔阂关注“知道如何做”，评估隔阂关注“知道做成没有”。输入、系统、输出与用户理解之间的转换可帮助定位问题，但无需每次画完整模型。

可用性要结合用户、任务和情境讨论。效率、成功、安全、易学、易记、效用与满意度可能有取舍；愉悦不能只凭设计者感觉判定，速度也不是所有产品的唯一目标。

## 原则与检查方向

| 原则 | 在任务中检查 |
| --- | --- |
| 状态可见 | 等待和结果是否能被判断 |
| 贴近用户概念 | 术语、映射和顺序是否可理解 |
| 控制与自由 | 能否退出、取消、返回和恢复 |
| 一致与惯例 | 同一含义是否同一行为，是否符合平台预期 |
| 防错 | 是否减少高代价误操作和输入歧义 |
| 识别胜于回忆 | 所需信息能否当场找到 |
| 灵活与效率 | 高频任务是否支持适当捷径 |
| 简约与重点 | 无关信息是否挤压关键内容 |
| 错误诊断与恢复 | 是否解释问题并指明下一步 |
| 帮助 | 是否能在任务中获得恰当说明 |

八条黄金规则可补充检查一致、普遍可用、反馈、操作闭环、防错、撤销、用户控制和记忆负担。“闭环”不是要求弹窗；两套规则无需硬性逐项对应。原则是判断依据，不是通用评分量表。

## 评审方法

启发式评估先理解主任务，再查看关键路径和局部状态。多人评估可独立记录后合并；一个 AI 多次自检不能报告为独立专家一致性。专家发现是待验证的判断，不等于用户必然受阻。

认知走查设定首次使用者的知识与目标，对每步判断：会不会形成合适的子目标、能否发现动作、能否理解动作与目标的关系、能否理解执行后的进展。记录依据，不以专家已知操作替用户推断。

## 可访问交互

优先使用合适的原生语义和现有可靠组件。检查键盘顺序、可见焦点、标签和错误关联；自定义交互必须同时实现行为与语义，添加 ARIA 属性本身不能修复缺失行为。

模态框打开时焦点进入内部，Tab 循环留在框内，提供关闭方式并支持 Escape；关闭后焦点回到触发点或合理的后续位置。初始焦点按内容与风险选择，不一律放第一个按钮。

状态消息应在适当情况下无需抢焦点也能被辅助技术感知；避免把所有更新设成打断性通告。核查固定头部或浮层是否遮住键盘焦点；“不能完全遮住”的最低要求与更严格“不能部分遮住”有区别。

若目标是 WCAG 2.2 AA，2.5.8 的最小目标尺寸为 24×24 CSS px，并有间距、等效控制、行内、用户代理和必要呈现等例外。它不是所有平台的推荐触控尺寸，不能替代完整符合性检查；按所选标准核查例外。

自动扫描可发现部分问题，仍需键盘、实际状态及目标辅助技术验证。仅有截图时不声称完成无障碍审计。

## 记录与排序

记录：位置/步骤、证据类型、实际或潜在行为、目标影响、原则、严重程度和理由、建议、验证方法。严重程度可用 0非问题、1表面、2轻微、3重要、4灾难，但不要与缺陷优先级 P0/P1 混淆。频率未知就写未知。

排序结合任务阻断、影响范围、失败代价、恢复能力和实施成本。自拟例：保存按钮可见但结果不明，静态图只能列“状态反馈待核查”；复现无反馈且用户重复点击后，才有行为证据支持更强结论。

复验要再次检查修改后的行为和可能回归的关键路径，不能只确认代码包含某个 CSS 类或文案。
